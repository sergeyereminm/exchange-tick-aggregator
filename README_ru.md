# Агрегатор биржевых котировок

Сбор котировок в реальном времени с трёх WebSocket-имитаторов бирж и запись в PostgreSQL.

English: [README.md](README.md).

Агрегатор параллельно подключается ко всем источникам, приводит сообщения к одному формату, отсекает дубликаты, держит ограниченную очередь и пишет тики в Postgres пакетами. Обрывы, «зависшие» сокеты и ошибки БД заложены в поведение системы, а не добавлены поверх спокойного сценария.

## Что нужно

- .NET 8 SDK
- Docker Desktop — если поднимать весь стек целиком
- По желанию: `psql` или любой клиент Postgres, чтобы посмотреть сохранённые тики

## Быстрый запуск (Docker Compose)

Из корня репозитория:

```bash
docker compose up --build
```

Поднимаются сервисы:

| Сервис | Назначение | Доступ с хоста |
|---|---|---|
| `postgres` | Хранение тиков | `127.0.0.1:15432` |
| `binance-style` | WebSocket-имитатор | `127.0.0.1:5001` |
| `coinbase-style` | WebSocket-имитатор | `127.0.0.1:5002` |
| `custom` | WebSocket-имитатор | `127.0.0.1:5003` |
| `aggregator` | Сбор, обработка, запись | порты наружу не публикуются; смотреть `docker compose logs aggregator` |

Postgres на хосте слушает порт **15432**, чтобы не пересечься с локальным Postgres на 5432.

В Compose у имитаторов сразу включены сбои: каждые 50 тиков уходит дубликат, после 200 тиков сокет закрывается (`DuplicateEveryTicks=50`, `DisconnectAfterTicks=200`). Переподключение и дедупликация проверяются непрерывно.

Посмотреть, сколько тиков уже в базе:

```bash
docker compose exec postgres psql -U aggregator -d ticks -c "SELECT source, COUNT(*) FROM ticks GROUP BY source ORDER BY source;"
```

Логи агрегатора (подключения, обрывы, метрики):

```bash
docker compose logs -f aggregator
```

### Поток имитатора в браузере

Адресная строка не открывает `ws://...`. Сделайте так:

1. В Chrome откройте `http://127.0.0.1:5001/ticks`. Ответ **400** — нормально: это WebSocket, не HTML.
2. `F12` → вкладка Console.
3. Вставьте:

```javascript
const ws = new WebSocket("ws://127.0.0.1:5001/ticks");
ws.onopen = () => console.log("connected");
ws.onmessage = (e) => console.log(e.data);
ws.onerror = (e) => console.error(e);
ws.onclose = (e) => console.log("closed", e.code, e.reason);
```

Пойдут JSON вроде `{"s":"BTCUSDT","p":"123.45","q":"0.12","T":...}`. Если консоль ругается на mixed content, сначала откройте именно `http://127.0.0.1:5001/ticks` или `about:blank`, затем снова вставьте код.

В Compose имитатор закрывает сокет после ~200 тиков — в консоли будет `closed`. Этот сниппет сам не переподключается; агрегатор переподключается отдельно.

Остановить:

```javascript
ws.close();
```

То же для портов `5002` и `5003` — формат JSON другой.

### Сбои по команде

У каждого имитатора есть небольшой HTTP API. Стек должен быть запущен.

Список команд:

```bash
curl http://127.0.0.1:5001/fault
```

Разорвать WebSocket (агрегатор должен переподключиться, остальные биржи продолжают работать):

```bash
curl -X POST http://127.0.0.1:5001/fault/disconnect
```

Ещё раз отправить следующий тик (агрегатор должен посчитать дубликат):

```bash
curl -X POST http://127.0.0.1:5001/fault/duplicate
```

То же из консоли Chrome на странице `http://127.0.0.1:5001/ticks`:

```javascript
await fetch("/fault/disconnect", { method: "POST" }).then(r => r.json());
await fetch("/fault/duplicate", { method: "POST" }).then(r => r.json());
```

Параллельно смотрите логи агрегатора:

```bash
docker compose logs -f aggregator
```

После `disconnect` появятся `connection ended` / `Reconnecting` / `Connected`. После `duplicate` в строке метрик вырастет счётчик `duplicate`.

Порты `5002` и `5003` — другие имитаторы. В Compose по-прежнему работают периодические сбои (`DuplicateEveryTicks` / `DisconnectAfterTicks`); HTTP-команды — дополнительно, в любой момент.

Остановить стек и удалить данные тома:

```bash
docker compose down -v
```

## Локальный запуск (агрегатор на хосте)

Удобно, когда правите воркер, а база и имитаторы остаются в Docker.

1. Поднимите Postgres и при необходимости имитаторы:

```bash
docker compose up --build postgres binance-style coinbase-style custom
```

2. Запустите агрегатор. В `appsettings.json` уже указаны `127.0.0.1:15432` и `ws://localhost:5001|5002|5003`:

```bash
dotnet run --project src/ExchangeTickAggregator
```

3. Имитаторы по отдельности, если Compose не используете:

```bash
dotnet run --project src/simulators/ExchangeSimulator.BinanceStyle
dotnet run --project src/simulators/ExchangeSimulator.CoinbaseStyle
dotnet run --project src/simulators/ExchangeSimulator.Custom
```

## Тесты

```bash
dotnet test
```

Проверяются не только штатные пути, но и поломки:

- дедупликация при одновременной записи из нескольких потоков
- очередь не растёт без ограничения
- пакетная запись, повтор при ошибке БД и счётчик отброшенных тиков
- экспоненциальная пауза перед переподключением и отключение по простою
- падение одной биржи не останавливает остальные

## Как устроено

```
Имитаторы (WS) ──► TickIngestionWorker (отдельный цикл на биржу)
                         │ разбор → дедуп → метрики
                         ▼
                   BoundedTickBuffer (Channel)
                         │
                         ▼
                 TickPersistenceWorker
                         │ пакетная запись + повтор
                         ▼
                      PostgreSQL
```

Правила (разбор, дедуп, очередь, пакеты, повторы) живут в `ExchangeTickAggregator.Core` и тестируются без хоста. Проект воркера связывает WebSocket, Npgsql, конфигурацию и фоновые сервисы (`IHostedService`).

### Новая биржа

1. Реализуйте `IQuoteParser` под её формат.
2. Зарегистрируйте формат в `QuoteParserFactory`.
3. Добавьте запись в `Exchanges` (имя, адрес, формат).

Цикл приёма и путь записи в БД менять не нужно.

## Решения и компромиссы

### Нормализация

У имитаторов намеренно разные сообщения:

| Источник | Поля | Тип цены | Формат времени |
|---|---|---|---|
| Binance-style | `s` / `p` / `q` / `T` | строка | Unix, миллисекунды |
| Coinbase-style | `product_id` / `price` / `volume` / `time` | число | ISO-8601 |
| Custom | `ticker` / `last` / `size` / `ts` | число | Unix-секунды строкой |

Все парсеры сводят это к одному `Tick`: тикер, цена, объём, время, источник.

### Дедупликация

- **Ключ:** `(Source, Ticker, Timestamp, Price, Volume)`
- **Окно:** 10 секунд (`Ingestion:DeduplicationWindowSeconds`)
- **Реализация:** `ConcurrentDictionary` и compare-and-swap, чтобы при конкурентном приёме с нескольких бирж решение accept/reject оставалось корректным

Компромисс: окно только в памяти текущего процесса. Отпечатки старше окна удаляются не чаще раза за окно, поэтому память ограничена недавними уникальными тиками без полного обхода словаря на каждый accept. После перезапуска тот же тик может попасть в базу снова. Вынести дедуп в отдельное хранилище убрало бы этот риск, но добавило бы задержку и сопровождение.

### Очередь и backpressure

Принятые тики идут в ограниченный `Channel<T>` (`Ingestion:BufferCapacity`, по умолчанию 10 000), режим `FullMode = Wait`. Если запись в БД отстаёт, потоки приёма ждут свободного места в очереди и не отбрасывают тики. Глубина очереди пишется в лог вместе с остальными счётчиками.

Компромисс: короткие просадки Postgres тики не теряют. Если база недоступна дольше, чем хватает повторов записи, приём может встать — см. [Запись в БД](#запись-в-бд).

### Запись в БД

- Пакет 500 строк или сброс раз в секунду (`Persistence:BatchSize` / `FlushIntervalMilliseconds`)
- Многострочный `INSERT` через Npgsql
- Таблица создаётся при старте (`CREATE TABLE IF NOT EXISTS ticks ...`)

Ошибка записи повторяется до `MaxWriteAttempts` раз (по умолчанию 3), с паузой `WriteRetryDelayMilliseconds` (по умолчанию 100 мс) между попытками. Если все попытки исчерпаны, пакет отбрасывается, растёт `DroppedTickCount`, в лог пишется ошибка. Тихое проглатывание исключений намеренно исключено: либо запись прошла, либо потеря видна в логах и метриках. Неудачный сброс оставляет пакет в памяти, чтобы следующая попытка писала те же тики.

Компромисс: после исчерпания повторов тики не сохраняются во внешнее хранилище. Outbox пережил бы более длинные простои БД; здесь отказ явный и ограничен памятью.

### Переподключение и простой

Каждая биржа крутится в своём цикле:

- пауза между попытками растёт экспоненциально (от 1 с до 30 с), со случайным разбросом, чтобы источники не переподключались синхронно
- если тики не приходят 15 с, зависший сокет закрывается
- сбой одного источника не отменяет остальные (`Task.WhenAll` и свой try/catch на биржу)

Имитаторы по настройке умеют закрывать сокет и повторять payload — эти пути можно проверять без ручной отладки сокетов.

### Мониторинг

Потокобезопасные счётчики: принято, битый JSON, дубликат, в очереди, записано, отброшено. Раз в 30 секунд воркер пишет в лог сводку счётчиков и текущую глубину канала.

### Остановка

При остановке хоста приём прекращается. Воркер записи разбирает ограниченную очередь и сбрасывает накопленный пакет в пределах `Persistence:DrainTimeoutMilliseconds` (по умолчанию 5 с). Если таймаут истечёт, часть тиков может не попасть в БД — см. [Что сознательно не сделано](#что-сознательно-не-сделано).

## Настройки

Основные параметры — в `src/ExchangeTickAggregator/appsettings.json`. Их же можно перекрыть переменными окружения, как в Compose.

| Раздел | Параметр | По умолчанию | Смысл |
|---|---|---|---|
| `Ingestion` | `BufferCapacity` | 10000 | Ёмкость очереди |
| `Ingestion` | `DeduplicationWindowSeconds` | 10 | Окно, в котором тик считается дубликатом |
| `Ingestion` | `IdleTimeoutSeconds` | 15 | Сколько ждать тиков, прежде чем считать соединение зависшим |
| `Ingestion` | `ReconnectInitialDelaySeconds` | 1 | Начальная пауза перед переподключением |
| `Ingestion` | `ReconnectMaxDelaySeconds` | 30 | Максимальная пауза перед переподключением |
| `Persistence` | `BatchSize` | 500 | Сколько строк в одном пакете |
| `Persistence` | `FlushIntervalMilliseconds` | 1000 | Принудительный сброс по таймеру |
| `Persistence` | `MaxWriteAttempts` | 3 | Сколько раз повторять неудачную запись |
| `Persistence` | `WriteRetryDelayMilliseconds` | 100 | Пауза между повторами записи |
| `Persistence` | `DrainTimeoutMilliseconds` | 5000 | Бюджет времени на разбор очереди и сброс пакета при остановке |

У имитаторов: `Simulator__TickIntervalMilliseconds`, `Simulator__DuplicateEveryTicks`, `Simulator__DisconnectAfterTicks`.

## Что сознательно не сделано

- У имитаторов нет TLS — это локальная демонстрация.
- Метрики только в логах, без Prometheus и Grafana.
- Дедупликация не переживает перезапуск процесса.
- После исчерпания повторов пакет БД отбрасывается (со счётчиком и логом), а не складывается в outbox.
- Если разбор очереди при остановке не уложился в `DrainTimeoutMilliseconds`, тики в канале или в накопленном пакете могут быть потеряны.
- Имитаторы слушают `0.0.0.0`, чтобы контейнеры видели друг друга. Эти порты не стоит открывать за пределы доверенной сети.
